# Component Inventory

The codebase deliberately splits UI into **three component territories**, each with a distinct purpose. Following the convention strictly is what keeps the App Router predictable — RSC by default, `'use client'` only where unavoidable.

| Territory | Path | Role |
|-----------|------|------|
| **Atomic primitives** | `src/components/ui/` | shadcn-generated Radix wrappers. Never feature-specific. |
| **Cross-feature shared** | `src/components/shared/` and `src/components/features/` | Components used by multiple feature modules or composed at the app shell level. |
| **Feature-local** | `src/features/<feature>/components/` | Owned by a single feature. Imports primitives upward, never sideways from other features. |

Conversely, **feature server actions** (`src/features/<feature>/actions.ts`) and **feature queries** (`src/features/<feature>/queries.ts`) live next to the components they serve.

## 4. Server vs. Client component map (current ratio)

- **Server Components** (default — no `'use client'`):
  - All `app/**/page.tsx`, all `app/**/layout.tsx`
  - `BackButton`, `SubmitButton` (no interactivity)
  - `CollectionList`
- **Client Components** (`'use client'` declared):
  - 18 components total — all interactive surfaces (forms, editors, dialogs, navigation)
  - Located mostly under `src/features/<feature>/components/` and `src/components/features/`

`'use client'` boundary discipline is good: client components are leaves of the tree, with Server Components owning data fetching and passing it down as props.

## 5. Form & validation pattern

The shadcn `form.tsx` primitive ties into `react-hook-form` + a Zod resolver. Pattern in this codebase:

```tsx
const form = useForm<z.infer<typeof schema>>({
  resolver: zodResolver(schema),
  defaultValues: { … },
});

<Form {...form}>
  <form onSubmit={form.handleSubmit(async (values) => { await someServerAction(values); })}>
    <FormField name="title" control={form.control} render={({ field }) => (
      <FormItem>
        <FormLabel>Title</FormLabel>
        <FormControl><Input {...field} /></FormControl>
        <FormMessage />
      </FormItem>
    )} />
  </form>
</Form>
```

Schemas live in `src/lib/validation/*.ts` (most modules) **or** `src/features/collections/schemas.ts` / inline in some prompt actions. Pick the lib location for reuse with server actions; co-locate when the schema is single-use.

## 6. Theming & styling conventions

- **Theme:** Kanagawa-inspired dark palette. The root `<html>` is hardcoded `className="dark"` in `app/layout.tsx`. Despite `next-themes` being installed, no light-mode toggle is wired up yet.
- **Colors:** Brand surfaces use literal hex (e.g. `bg-[#16161D]`, `bg-[#1F1F28]`, `text-[#DCD7BA]`). Per CLAUDE.md, this is the intended convention — do not migrate to CSS variables without coordination.
- **`cn()`:** From `src/lib/utils/cn.ts` — `clsx` + `tailwind-merge`. Use it for any conditional class composition.
- **Layout target:** Optimized for **~400px viewport width** (mobile sidecar / extension contexts); use `md:` breakpoints for wider viewports.

## 7. State management — there is no global store

I want to flag this clearly because it's a deliberate architectural choice, not an omission:

- **No Redux, Zustand, MobX, Recoil, Jotai, or similar.**
- **No app-level `createContext`** (the only `createContext` in the codebase is the shadcn `Form` primitive).
- **No `useReducer`** anywhere.

Instead, the codebase relies on:

1. **Server Components fetch data** and pass it down as props.
2. **Client components manage local UI state only** with `useState` + `useEffect`.
3. **Mutations call Server Actions**, which call `revalidatePath('/')` (or `/profile`, `/prompts/${id}`) to invalidate page caches.
4. **The next request re-renders the Server Component** with fresh data, which then flows back into the client component via props.
5. **Side-channel UI feedback** uses `sonner` toasts and direct `cn()`-driven className flips.

This pattern (RSC + Server Actions + revalidate) is the **architectural identity** of the project — adding global state would fight against it. If you find yourself needing cross-component shared state, the order of preference is:

1. Lift state to the closest common ancestor client component.
2. Store the source of truth in the database, fetch via Server Component props.
3. Use URL search params (`useSearchParams`) for state that should survive a refresh.
4. Only as a last resort: introduce a context provider, scoped tightly.

## 8. Keyboard shortcuts

| Shortcut | Where handled | What it does |
|----------|--------------|--------------|
| `Cmd+K` / `Ctrl+K` | `CommandPalette` (`features/search/command-palette.tsx`) | Open global search palette |
| Arrow-up / Arrow-down | `PromptList` | Navigate prompt rows |
| `Ctrl+C` / `Cmd+C` | `PromptDetail` editor | Copy resolved prompt |
| Native paste | Editors | Standard browser paste |

These are documented in CLAUDE.md and worth preserving — they are part of the product's identity (designed for the keyboard-driven sidecar use case).
